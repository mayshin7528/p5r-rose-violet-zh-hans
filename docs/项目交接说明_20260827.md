# Rose & Violet 简体中文补丁项目交接说明

日期：2026-08-27

## 1. 项目目标

本工程为《Persona 5 Royal》Rose & Violet Mod 的简体中文补丁，包含：

- 可直接由 Reloaded-II 加载的汉化 Mod 文件；
- Mod 英文、官方中文参考与最终中文组成的文本目录；
- 人工译文覆盖库、构建脚本及编译部署流程；
- 本地翻译管理器和供测试人员使用的便携审核器；
- 强制中文主角姓名的集成 DLL。

仓库位置：`F:\Rose\p5r-rose-violet-zh-hans`

本机安装位置：`F:\Reloaded-II\Mods\p5rpc.kasumi.roseandviolet.zh-hans`

## 2. 最重要的接手规则

1. **原 Mod 英文是唯一语义基准，必须逐句阅读。**
2. 官方简体中文只用于术语、角色口吻、标点和中文表达参考。
3. `EXACT_OFFICIAL_PROXY`、相同路径和相同消息 ID 只证明结构可以对齐，不能证明语义相同。
4. 说话人、性别、指代、人物关系、选项分支和日期场景都必须按 Mod 英文及上下文确认。
5. 主角是芳泽霞；Mod 英文中的 Sumire 是芳泽堇。
6. 动态姓名、消息头、分页和控制码必须保留；结构性 `Dummy` 不得翻译。
7. 没有明确逐句对照记录的文本必须保持“未核对”，不能因已有中文或 override 自动通过。
8. 当前工作区包含大量尚未提交的有效成果，**禁止使用 `git reset --hard`、`git checkout -- .` 或批量清理未跟踪文件**。

正式标准见：`docs/翻译审核标准.md`。

## 3. 已完成的主要工作

### 3.1 文本基础库与覆盖体系

- 建立了约 187,753 条文本记录、3,799 个资源的目录。
- `translations/catalog/*.csv.gz` 保存 Mod 英文、官方中文参考、结构信息和基础中文。
- `translations/overrides.csv` 是人工最终译文的权威来源，包含更新时间、编译时间和核对时间。
- `translations/resource_status.json` 保存各资源最近一次构建状态。
- 构建器会保留结构性 `Dummy`，并跳过仍含整句英文的资源，避免用半汉化文件覆盖游戏资源。

### 3.3 翻译管理器

运行仓库根目录的 `start_translation_manager.cmd`，访问 `http://127.0.0.1:4178/`。

已经实现：

- 按路径、消息 ID、说话人和内容搜索；
- 按分类及状态筛选；
- 同时显示 Mod 原始 header、Mod 英文和最终中文；
- 编辑中文并写入 `translations/overrides.csv`；
- 手动标记“已核对”及取消核对；
- 已核对文本锁定，防止后续误改；
- 按所选资源编译、部署、备份并处理 ModLoader 缓存；
- 显示已编辑、已核对、未核对、编译失败、英文残留等状态。

管理器只信任 `reviewed_at`，不会自行判断审核是否符合严格标准。因此只有实际对照过 Mod 英文和上下文的条目才能点击“已核对”。

### 3.4 便携审核器与多人协作

构建脚本：`tools/build_portable_translation_manager.js`

产物目录：`dist/Rose-Translation-Reviewer/`

测试人员可运行 `start_reviewer.cmd`，无需安装 Node.js。便携版可搜索、编辑、核对，但不能编译或直接修改维护者主库。

协作流程：

1. 测试人员在便携版修改和核对文本。
2. 点击“保存审核结果”，生成带时间戳的 `rose-review-*.json`。
3. 维护者在主管理器导入该 JSON。
4. 未冲突内容自动合并；双方都改过同一句时，维护者逐条选择版本。
5. 维护者可导出 `rose-master-update-*.json` 给测试人员更新主库，无需重发整套便携包。
6. 测试人员导入更新包时，本地尚未导出的审核记录会保留；冲突项同样逐条选择。

主库更新、冲突预览、保留测试员本地译文和自动重启流程已经通过隔离 API 测试。

## 4. 当前状态与风险

### 4.1 旧审核标准尚未完全隔离

正式新标准已经写入 `docs/翻译审核标准.md`，但旧文件仍留作历史记录。

危险旧脚本：

- `scripts/generate_third_semester_audit.js`

该脚本仍含“`EXACT_OFFICIAL_PROXY` 即 Mod 未改、可沿用官中”的旧逻辑。当前管理器和编译流程不会自动调用它，但接手人不得手动运行并采用其结论。

8 月 9 至 10 日的旧审核报告只可用于定位历史问题，不能作为“已核对”证明。当前约 1,057 条记录带有 `reviewed_at`，其中大部分来自后续精翻和截图修正，但也包含早期称呼修复来源。严格发布前应按审核来源重新确认，无法证明逐句对照英文的条目应恢复为未核对。

### 4.2 Git 工作区非常脏

- 当前仓库只有一个初始化提交：`89649a3`。
- 后续大量编译资源、译文、报告、脚本和管理器改动尚未形成整理后的提交。
- `git status` 包含大量新增、修改、删除和未跟踪文件。
- 不要依据初始化提交回滚当前目录，也不要假设未跟踪文件可以删除。

建议先完整备份当前目录，再按“源码／最终资源／历史报告／临时产物”分批整理提交。

### 4.3 DLL 不一致

仓库根目录 `RoseVioletChineseName.dll` 与已安装 Mod 中同名 DLL 的 SHA-256 当前不一致，文件大小也不同。发布前必须确认哪一个是正确集成版本，重新构建或同步后，再核对仓库与安装目录哈希，并进行游戏内姓名显示测试。

### 4.4 便携 ZIP 可能过期

`dist/Rose-Translation-Reviewer/` 是 2026-08-26 重新生成的新目录，包含主库更新功能。已有 ZIP 可能早于该目录，发送给测试人员前应重新压缩当前目录，不要直接使用旧 ZIP。

### 4.5 仍有未完成文本

- 大量文本仍处于“未核对”；不能把“已有中文”视为完成。
- 仍含整句英文的资源会被构建器跳过。
- NPC、场景交互和部分女主相关剧情仍需按严格标准逐句核对。
- 游戏内复测仍是最终判断依据，尤其是说话人、分页、动态姓名、选项分支和缓存覆盖问题。

## 5. 常用命令

启动管理器：

```powershell
.\start_translation_manager.cmd
```

构建便携审核器：

```powershell
node tools/build_portable_translation_manager.js
```

全量构建：

```powershell
node --max-old-space-size=8192 scripts/build_translation_patch.js --build
```

准备发布树并部署：

```powershell
node scripts/prepare_release_tree.js
node scripts/deploy_translation_build.js
node scripts/mark_deployed_overrides.js
```

本机若 `node` 不在 `PATH`，可使用便携目录中的 `dist/Rose-Translation-Reviewer/node.exe`。

## 6. 推荐接手顺序

1. 完整备份仓库和已安装汉化 Mod。
2. 阅读 `docs/翻译审核标准.md`，不要沿用旧报告结论。
3. 处理 DLL 哈希不一致并完成游戏内姓名测试。
4. 整理 Git 工作区，先提交管理器、译文源和审核报告，再处理大批编译资源。
5. 在管理器中只处理“未核对”条目，逐句对照 Mod 英文和上下文。
6. 对修改资源做小范围编译、部署、哈希核对和冷启动游戏测试。
7. 稳定后再做全量构建与发布包。

## 7. 不应做的事

- 不要用官中覆盖 Mod 英文已经改变的剧情。
- 不要根据 `EXACT_OFFICIAL_PROXY` 自动放行。
- 不要翻译结构性 `Dummy`。
- 不要写死动态姓名控制码。
- 不要同时运行两个主角姓名 hook。
- 不要把“编译成功”描述成“游戏内验证成功”。
- 不要清理或回滚当前脏工作区，除非已经完成可恢复备份并确认文件归属。
